# Журнал ошибок проекта rummi-local

## 2026-11-22 — На экране настройки в ландшафте нельзя прокрутить вверх

- **Источник:** владелец (скриншот с Android).
- **Суть и последствия:** на экране настройки (`#screenSetup`) в горизонтальной ориентации телефона верхняя часть формы (логотип, «Продолжить», «Сколько игроков») уходила за верхний край и была недоступна для прокрутки вверх — мотать можно было только вниз.
- **Причина (класс проблемы):** сочетание `display: flex; flex-direction: column; justify-content: center; overflow-y: auto;` — когда дочерний блок выше контейнера, `justify-content: center` смещает его верх в отрицательные координаты, до которых скролл-контейнер не докручивает.
- **Исправление и проверка по классу:**
  - Проверены все скроллируемые flex-контейнеры в `styles.css` (`#screenSetup`, `.board`, `.rack`, `.sel-panel`, `.overlay-card`).
  - В `#screenSetup` убран `justify-content: center` (`flex-start`), на `.setup-card` добавлены `margin: auto 0; flex-shrink: 0;` — вертикальное центрирование на высоких экранах сохраняется, а при переполнении верхний край всегда начинается с `y = 0` и прокрутка работает в обе стороны.
  - В `.sel-panel.is-idle` (включая `body.land .sel-panel.is-idle`, где при `640×280` подсказка уходила на `-9 px` выше края) также убран `justify-content: center` в пользу `justify-content: flex-start` + `margin: auto` на `.sel-hint`.
  - Для `.overlay-card > *` добавлен `flex-shrink: 0`, чтобы элементы модалок не сжимались на низких ландшафтных экранах.
  - Поднята версия кэша в `sw.js` до `rummikub-v14`.
  - Проверено в браузере (844×390, 800×360, 430×932) и тестами (`npm test`, 67/67).
- **Вывод:** на прокручиваемых flex-контейнерах никогда не использовать `justify-content: center` по оси прокрутки; для центрирования использовать `margin: auto` на дочернем элементе.

## 2026-11-22 — После `git push` не проверен статус CI (`Deploy to GitHub Pages`)

- **Источник:** владелец («Ci упал. Ты почему не проследил?»).
- **Суть и последствия:** после `git push origin main` (`c9669ac`) я сразу сообщил владельцу, что через минуту обновление подтянется на телефон, не проверив фактический результат workflow `Deploy to GitHub Pages` (`run 45064626739`). Деплой упал из-за гонки в GitHub Artifacts API (`deploy-pages@v4` запросил метаданные через 0.3 с после финализации артефакта и получил `Found 0 artifact(s)`), и новая версия `rummikub-v14` не выложилась.
- **Причина (нарушенный принцип):** принцип «Доводи до его результата, а не до своего артефакта» — я принял сам `git push` за готовый результат, хотя для владельца результат наступает только после успешного деплоя на GitHub Pages.
- **Исправление и проверка:**
  - `gh run rerun --failed` в том же run привёл к дубликату артефакта (`Found 2 artifact(s)` — `upload-pages-artifact` и `deploy-pages` живут в одном job). Запущен свежий run через `gh workflow run pages.yml --ref main` и поставлена проверка до фактического `success` и живого `sw.js`.
  - В `AGENTS.md` закреплено правило: после каждого `git push` в `main` проверять статус `Deploy to GitHub Pages` до `completed / success` прежде чем рапортовать о выкладке.
- **Вывод:** `git push` — это не завершение выкладки; завершение выкладки — подтверждённый `success` в CI/CD. При сбое `deploy-pages` перезапускать не `gh run rerun`, а новый `gh workflow run pages.yml --ref main`.

## 2026-11-22 — В ландшафте на Android шапка и лоток съели почти половину высоты экрана, сжав стол

- **Источник:** владелец (скриншот 2000×897 / ~870×390 с Android после `rummikub-v14`).
- **Суть и последствия:** при `--tile-w: clamp(34px, 9.8vh, 42px)` и пропорции `1.36x` фишки стали высокими (`~38×52 px`), шапка занимала `~50 px`, а лоток на 18 фишках (14 в первой строке + 4 во второй) — `~132 px`. Столу оставалось меньше половины экрана (`~200 px`, еле 2 ряда наборов).
- **Причина:** при увеличении целей под палец не контролировалась вертикальная пропорция фишек и суммарная доля высоты шапки + лотка на коротком ландшафтном экране (`360–390 px`).
- **Исправление:**
  - В `body.land` / `body.land.is-rot` фишки сделаны чуть менее вытянутыми (`--tile-h: calc(var(--tile-w) * 1.2)`, `--tile-w: clamp(32px, 8.8vh, 38px)`, `--gap: 4px`), шапка сжата до `~37 px`, отступы `.rack-area`/`.rack`/`.board`/`.meld` уплотнены, боковая панель сужена с `188px` до `170px`.
  - Проверено в браузере (870×390, 800×360, 667×375, `is-rot`): на `870×390` стол получает `300 px` (77%, 4 полных ряда) при 14 фишках и `255 px` (65%, 3 полных ряда) при 18; на `800×360` — `273 px` (76%, 4 ряда) и `230 px` (64%, 3 ряда); на `667×375` — `243 px` (65%, 3 ряда). В обычной раскладке минимум `fitRack` оставлен `34 px`.
  - Поднята версия кэша в `sw.js` до `rummikub-v15`.
- **Вывод:** на мобильном ландшафте (высота 360–390 px) нужно отдельно мерить реальную высоту `.hud`, `.board` и `.rack-area` на 14 и 18 фишках — столу должно оставаться не меньше ~64% высоты даже при 2 рядах лотка (3+ полных ряда наборов).
